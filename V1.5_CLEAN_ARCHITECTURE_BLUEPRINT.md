# InteriorPro V1.5 - Clean Architecture Blueprint

## 1. Target Architecture

The new V1.5 architecture enforces a strict unidirectional data flow and a Single Source of Truth for calculations.

```text
RAW INPUT
    ↓
VALIDATION
    ↓
CALCULATION ENGINE (Domain Layer)
    ↓
CALCULATION RESULT
    ↓
QUOTATION SNAPSHOT (Immutable historical record)
    ↓
┌─────────────────────┬─────────────────────┐
│                     │                     │
UI DISPLAY            DATABASE              PDF RENDERER
│                     │                     │
Display Result        Persist Snapshot      Render Snapshot
│                     │                     │
└─────────────────────┴─────────────────────┘
```

## 2. Responsibility Matrix

| Module | Responsibility | Allowed | NOT Allowed |
|--------|----------------|---------|-------------|
| **UI** | Input and display | User interaction, display finalized results | Business calculations |
| **ViewModel** | Screen state | Call Use Cases, hold UI state | Direct PDF generation, business calculations |
| **Use Case** | Application workflow | Coordinate operations, trigger calculation | Duplicate calculations |
| **Calculation Engine** | All business calculations | Calculate authoritative results, parse units | UI/PDF rendering |
| **Repository** | Data access | Read/write data | Business calculation |
| **Database** | Persistence | Store data/snapshots | Recalculate values |
| **PDF Data Preparation**| Prepare render-ready data | Map finalized snapshot to PDF models | Recalculate business logic |
| **PDF Renderer** | Visual rendering | Draw PDF text/tables/images | Recalculate billable qty/totals |
| **Backup/Restore** | Data portability | Export/import database | Alter business rules |

## 4. Raw Input vs Calculated Snapshot

**Raw Input** (Mutable, what the user enters):
- Dimension Strings (e.g. `10'6"`)
- Raw Quantity (e.g. `1`)
- Unit (e.g. `Sq.Ft`)
- Rate
- Discount, Transport, Installation, Extra Charges input
- Advance Payment input

**Calculated Snapshot** (Immutable historical result):
- All fields in `CalculationResult` (Billable Qty, Item Amount, Subtotal, GST, Grand Total, Balance)
- Converted parsed dimensions (in feet/meters)

**Status:** The DB MUST store the calculated snapshot. Once a quote is saved, its calculated values are locked.

## 5. Quotation Snapshot Design

To preserve historical accuracy, a Quotation must capture all external data at the time of creation.
If Masters change tomorrow, old Quotations remain intact.

- **Customer Snapshot**: Saved explicitly in the Quotation record (already partially done).
- **Company Snapshot**: Must capture Company Name, Address, Contact, Logo Path, GSTIN, Bank Details at the time of PDF generation or quote creation. (REQUIRES PRODUCT DECISION: Do we snap Company Profile on Save or on PDF Gen?)
- **Terms Snapshot**: Assembled terms saved as a block of text in the quotation. (Currently `termsAndConditions`).
- **Payment Snapshot**: Captured advance and balance.
- **Item Snapshot**: Dimensions, Rate, and `billableQuantity` explicitly saved.

## 7. Unit & Dimension Engine

Isolates dimension string parsing and billable quantity logic.

- **Current Implementations**: UI parses/calculates inline; PDF recalculates using `amount/rate` or `calculateQuantity`.
- **Conflict**: Billable Qty divergence.
- **Required Resolution**: Engine exposes `fun calculateItem(...) : CalculatedItem`. UI and PDF strictly consume `CalculatedItem.billableQuantity`.

## 8. PDF Architecture

**Current**: PDF Engine queries DB, recalculates totals, recalculates item qty, evaluates terms, draws UI.
**Target**:
`PdfDocumentModel` (Pure Data Class, fully pre-calculated)
-> `PdfRenderer` (Only draws what is given)

PdfRenderer MUST NOT:
- Calculate area/volume/qty
- Calculate GST/Subtotal/Grand Total
- Assemble Terms dynamically (should be passed pre-assembled)
- Read raw dimension strings to derive totals

## 9. PDF Module Decomposition

The 1736-line monolithic `PdfGenerator.kt` will be split into:
1. `PdfDocumentBuilder` (Maps Snapshot -> `PdfDocumentModel`)
2. `PdfPageManager` (Handles canvas, pagination, Y-offsets)
3. `PdfHeaderRenderer` (Company Branding)
4. `PdfCustomerRenderer` (Client Info)
5. `PdfItemTableRenderer` (Lines and measurements)
6. `PdfFinancialRenderer` (Totals and amount in words)
7. `PdfTermsRenderer`
8. `PdfFooterRenderer` (Signature, Bank, QR)

|---|---|---|---|---|

| Draft Quote | `QuotationDraft` | ViewModel | Yes | No |
| Calculation | `CalculationResult`| Engine | No | No |

| PDF Model | `PdfDocumentModel`| PDF Builder| No | No |
| Visual PDF | `.pdf` file | FileSystem | No | Yes |

## 11. Edit Quotation Flow

1. Open Existing Quotation
2. Load Snapshot (`QuotationEntity` -> `QuotationDraft`)
3. Edit Raw Inputs in UI
4. Recalculate using Calculation Engine (creates new `CalculationResult`)
5. Update Quotation Snapshot
6. Persist to Database
7. Generate PDF from updated Snapshot

## 12. Error Handling Contract

| Error | Detection Layer | User Message | Recovery |
|---|---|---|---|
| Invalid Dimensions | Validation / Engine | "Invalid dimension format" | Prompt user to correct input |
| Zero/Negative Qty | Engine | "Quantity must be > 0" | Reset to 1 or block save |
| Calculation Overflow| Engine | "Values exceed maximum limit" | Block calculation |
| PDF Gen Failure | PDF Renderer | "Failed to generate PDF" | Log error, allow retry |

## 16. Critical Architecture Decisions

1. **Single Source of Truth**: CONFIRMED. `CalculationEngine` generates immutable `CalculationResult`.
2. **3-Way Divergence**: CONFIRMED. DB must store `billableQuantity`. PDF must read it.
3. **Company Profile Changes**: REQUIRES PRODUCT DECISION. If Company changes, does old PDF change? (Typically yes for generic profile, no for legal terms).
4. **Rate Master Changes**: CONFIRMED. Old quotations are immutable. Rate changes do not affect past quotes.
5. **PDF Calculation Prohibition**: CONFIRMED. PDF is strictly a renderer.
